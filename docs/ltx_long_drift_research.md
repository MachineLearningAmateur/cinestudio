# Colour / identity drift in chained LTX-2.5 clips: what Lightricks, the research and the community do, mapped onto cinestudio

Date 2026-10-22. Tags: [OFFICIAL] Lightricks docs / model cards, [CODE] read in source (repo + file + commit), [RESEARCH] papers, [COMMUNITY] forum posts, [INFERENCE] my reasoning.


> **Correction (checked 2026-10-22 after the report):** the frame -1 claim in 1.1 (last bullet but one) is true for ComfyUI core `LTXVAddGuide`, but NOT for the node our layout graphs use: `LTXAddVideoICLoRAGuide` (ComfyUI-LTXVideo `iclora.py` 137-163, `resolve_frame_idx`) returns a negative index unchanged: "A negative value is a RoPE position before the clip, not an index counted back from its end". Our look image sits BEFORE the clip (as AGENTS.md says), not at frame 120.

## 0. One-paragraph answer

Lightricks' own long-video tool (LTXVLoopingSampler / LTXVExtendSampler) chains clips the way we do (the previous tile's last latents pinned as an appended guide, linear latent cross-fade over the overlap) and then fights drift with exactly three levers, all inference-only: (1) AdaIN of every later tile toward the **first tile's output latent** (not the previous tile, not an image), factor 0.1-0.3; (2) an optional **global anchor latent fed identically to every chunk** at a negative index ("long memory"); (3) pixel keyframes per chunk at strength 1.0. We do (1) with a different reference (the look image, factor 0.5) and (2) with a *moving* anchor (the chained frame), which is the textbook recipe for error accumulation: the research (Rolling Forcing, LongLive, ID-Forcing, FramePack) agrees that the anchor must be the **first** chunk, kept fixed, and that the neighbour-only chain drifts. The cheapest tests: give every clip the run's first look as the fixed anchor and carry the join through a frame-0 guide instead (zero code), switch the AdaIN reference to clip 1's saved latent (one small change), and colour-match the chained frame to clip 1 in pixel space over the whole frame, not only dark pixels.

## 1. Lightricks' own guidance

### 1.1 ComfyUI-LTXVideo (installed pack, commit 220e1d4, 2026-10-20)

- [CODE] `looping_sampler.md`: "Each temporal tile is conditioned on the **end frames** of the previous tile"; defaults `temporal_tile_size` 80, `temporal_overlap` 24, `temporal_overlap_cond_strength` **0.5**; best practice "`temporal_overlap` = 1/3 of `temporal_tile_size`", "Set `adain_factor` = 0.1-0.3 for long sequences to prevent oversaturation". Troubleshooting: "**Color Shifts: Use `optional_normalizing_latents` for reference and/or increase `adain_factor`**"; "Oversaturation: increase `adain_factor`". `adain_factor`: "AdaIn is applied on each new temporal tile, **with respect to the latent statistics of the first temporal tile**." `optional_negative_index_latents`: "Each temporal chunk is conditioned on the provided negative index latent(s) using negative positional embeddings ... reference global context or style cues throughout the video, reducing drift ... Referencing a global template or anchor image".
- [CODE] `looping_sampler.py` ~l.370-395: without normalizing latents, `normalizing_latent_chunk = first_tile_out_latents`, `normalize_per_frame = False` ("normalizing per channel using first chunk"). With normalizing latents: per frame, each tile against its counterpart.
- [CODE] `easy_samplers.py` `LTXVExtendSampler` (l.301-640): the previous tile's last `overlap` latents are pinned with `add_latent_guide(... latent_idx=0, strength=strength)` (default 0.5) — i.e. **appended as a guide, like our relay**, not written in place; three sigma phases (overlap only / overlap + guiding latents + keyframes + negative-index latent / overlap + keyframes); keyframes via `LTXVAddGuide` at `cond_image_strength` 1.0; the negative-index latent via `add_latent_guide(latent_idx=optional_negative_index (-1), strength=1.0)`; **after** denoising, `LTXVAdainLatent().batch_normalize(denoised, reference=optional_reference_latents, factor=adain_factor)`, the first output latent dropped, then `LinearOverlapLatentTransition().process(latents, new, overlap - 1, axis=2)` (a linear latent cross-fade over the overlap; class at easy_samplers.py l.847). No pixel colour correction anywhere.
- [CODE] `latent_norm.py` `LTXVAdainLatent`: per batch and **per channel**, global std/mean over F×H×W (or per frame with `per_frame`), `t = (t - i_mean)/i_sd * r_sd + r_mean`, then `lerp(original, t, factor)`; factor range -10..10. Note the reference is a LATENT of any frame count; a 1-frame image latent (our look) is a legal but out-of-practice reference: Lightricks' reference is a whole video tile from the same sampler.
- [CODE] `latents.py` `add_latent_guide`: "Pin an already-encoded latent as a guide, via ComfyUI's native node"; without an attention mask the attention strength is reset to 1.0 so `strength` only sets the latent's noise-mask pin.
- [CODE] ComfyUI core `comfy_extras/nodes_lt.py` (ComfyUI 63be2f9b, 2026-10-18): `LTXVAddGuide.execute` resolves a negative `frame_idx` as `max((latent_count - 1) * 8 + 1 + frame_idx, 0)` -> **frame -1 is the position of the LAST pixel frame (120 of 121)**, Python-style; the guide is appended (`append_keyframe`: `torch.cat` at the end, mask `1 - strength`) with that RoPE time. So in ComfyUI our frame -1 look is "a held frame time-stamped at the clip's end", not a time-less token. [INFERENCE] The chained look (clip k-1's frame 96 = clip k's frame 0) is therefore stamped 120 frames late; it still works as a palette/material anchor because attention ignores the pose, but the time stamp is one more reason the model does not treat it as a hard start frame.
- [CODE] Example workflows: only `2.0/LTX-2_V2V_Detailer.json` uses the looping sampler (tile 56, overlap 24, cond strength 0.5, adain 0). No 2.3/2.5 example chains clips; the 2.5 README lists T2V/I2V, IC-LoRAs and tiled-fusion only.

### 1.2 LTX-2 repo (Lightricks/LTX-2, main, read 2026-10-22)

- [CODE] `ltx_pipelines/chunks/layout.py` `ChunkConfig`: `chunk_pixel_frames = 97`, `next_video_carry_frames = 25`, `overlap_blend_frames = None -> carry`; docstring: the matching tail is "sliced from the end of the video (and audio) latent" and "pinned at index 0 for continuity"; the re-rendered overlap frames are "dropped after decode" and the decoded tails cross-faded. So Lightricks' new chunked pipeline = 25-frame carry (4 latents) pinned at index 0 + a decoded cross-fade: the same shape as our relay + flow blend.
- [CODE] `chunks/conditionings.py` + `planner.py`: images are kept only in the chunk whose window contains their index ("Point items map through ChunkLayout.local_frame_index; span items apply to every window"); IC-LoRA reference videos are **sliced** per chunk; **no first-frame or reference re-injection** by default. "Generated keyframes" (a 2.5 feature: `LTXVAddGeneratedKeyframes`, needs a checkpoint with `keyframes_abs_pos_embedding`) are planned per chunk with "one slot at their seam"; each chunk receives the previous chunk's keyframe planes "rebased onto this chunk's local timeline for fixed conditioning".
- [CODE] `retake.py`: regenerates a time window inside an existing video with a `TemporalRegionMask`; no strength knob, no drift notes.

## 2. Research on drift in chunked / autoregressive video

- [RESEARCH] FramePack (arXiv 2504.12626, Zhang & Agrawala 2025): drift = "error accumulation", a forgetting/drifting trade-off; **anti-drifting sampling** generates in inverted order "with early-established endpoints" so every chunk is bounded by clean anchors; Diffusers exposes `inverted_anti_drifting`. Needs a model trained for that order for frame-level use, but [INFERENCE] the *principle* is inference-only at the shot level for us: make the shot's anchor images first (start and end of each clip from one consistent source), then fill each clip between them.
- [RESEARCH] Rolling Forcing (arXiv 2509.25161, ICLR 2026): an **attention sink** keeps "key-value states of initial frames as a global context anchor" (3 latent frames); removing the sink raises their drift score from 0.01 to 4.63 and subject consistency falls 92.8 -> 83.2; joint denoising of a rolling window. Trained; the sink idea itself is just "always attend to the first chunk".
- [RESEARCH] LongLive (arXiv 2509.22622, ICLR 2026): "frame sink" + KV-recache on prompt change; trained (32 GPU-days on a 1.3B model).
- [RESEARCH] Self Forcing (arXiv 2506.08009, NeurIPS 2025): trains on the model's own rollouts (exposure bias); rolling KV cache; training only.
- [RESEARCH] **ID-Forcing** (arXiv 2610.03120, Oct 2026): **training-free, test-time**; "the first chunk's KV entry stays permanently in slot 0 as a sink" and every chunk is cached "without attending to prior KV entry" so the window stays in-distribution; drift metrics: **Color Drift = L1 between 180-bin hue histograms of the first and last frame**, Motion Drift = dynamic-degree difference; tested on Self-Forcing and LongLive. The paper's related-work list of anchor mechanisms: attention sinks, Deep Forcing (early KV as sinks + RoPE realignment), ∞-RoPE, MemRoPE.
- [RESEARCH] Helios (arXiv 2603.04379): simulates drift during training; training only.
- [RESEARCH] LAMP (CVPR 2024, arXiv 2310.10769; supplement not fetchable, cited by the search engine): AdaIN of later frames toward the **first frame** in the early denoising steps only ("applying it throughout produced artifacts") plus pixel-space histogram matching: a precedent for AdaIN-to-the-first-frame, early steps only.
- [RESEARCH] AnchorSync (arXiv 2508.14609) and FlowLong (2605.20910): anchor-frame / overlapping-window blending for long editing and generation; inference-time but tied to other backbones.
- [INFERENCE] Common thread: every method that works keeps the **first** chunk as a permanent, unchanged anchor; neighbour-only conditioning (what our chained look + relay does) is the drifting baseline in every paper. Our measured symptom (frame 0 and 345 share camera and light but not colours) is exactly their "colour drift first-vs-last".

## 4. Mapping onto cinestudio and what to test

What we do today (runner.py, `_layout_clips`, graph `ltx25_layout_api.json`): `g_lay` layout at frame 0 (1.0), `g_look` at frame -1 (1.0, i.e. time 120), Ingredients sheet, relay = clip k-1's last 3 latents appended at latent index 1 (strength 1.0; Lightricks' default for the same pin is 0.5), `add_adain` toward the **look image's** latent (factor 0.5, per_frame False), chained look = clip k-1's frame 96 sharpened, keyframes as extra `LTXAddVideoICLoRAGuide` copies. Everything below is inference-only and uses installed nodes.

| Idea | Nodes | Cost / risk |
|---|---|---|
| A. Fixed global anchor = the run's first look in every clip; the join carried by the chained frame as a frame-0 guide | `g_look` (run look) + `add_keyframe_guides([(0, chained)])` | 0 code; risk: two looks compete, the start background from the run look (what broke `--look-chain run` alone) |
| B. AdaIN reference = clip 1's saved stage-1 latent (Lightricks' choice), factor 0.2-0.5 | `LoadLatent(relay_<run>_1_s1)` -> `LTXVAdainLatent` | ~10 lines in `add_adain`; global per-channel stats: corrects the scene palette, the costume only partly |
| C. Pixel colour match of the chained look to clip 1 frame 0 (whole frame; MKL or Reinhard in Lab), optionally costume pixels matched to the look's costume by the Blender mask | OpenCV / `color-matcher`, before upload | 0 GPU; risk: the relay latents still carry the drifted colours, the look must win (the e2e test says frame -1 is the strong lever); dark-pixels-only shift made the jacket blue, so match the whole frame |
| D. Lower the relay strength (0.5, Lightricks' default) when a corrected look is given | `relay_strength` | 0 code; weaker join, measure `overlap` |
| E. Shot-level anchors made first: sheet panel or Qwen look pasted at each clip's start AND end frame (the card's "mid frame and a last frame") from one consistent source | `add_keyframe_guides` | the e2e test showed keyframes are weak vs frame -1 and A-pose panels fight the rig; use pose-matched (Blender-frame) looks |
| F. Post-decode colour match of every clip to clip 1 for the OUTPUT only | OpenCV per frame | 0 GPU, no effect on the chain; a safe cosmetic fallback for the final video |
| G. Longer overlap (Lightricks: 1/3 of the tile = 41 frames for 121) | `overlap` | more clips per shot; does not stop drift, only softens joins |
| H. Per-step AdaIN (LTXVPerStepAdainPatcher / StatNormPatcher, LAMP's "early steps only") | pack nodes | untested on IC-LoRA graphs; try after B |

**Measure every take with:** our Lab b* of the costume's dark pixels in the Blender mask, plus ID-Forcing's colour-drift number (L1 between the 180-bin hue histograms of the clip's last frame and clip 1's frame 0), plus `run score` `overlap` for the join.

### Top 3 experiments (one retake each, ~3 min of GPU at preview)

1. **Fixed anchor + join guide (A + D).** `run retake RUN --clip 3 --seed <same> --look-chain run --keyframe-image <run>/parts/look_chain_3.png --keyframe-frame 0 --keyframe off --relay-strength 0.5 --note "run look as the fixed anchor; chained frame as a frame-0 guide"`. Hypothesis: the run's look holds the palette (Lightricks' "global template or anchor image" fed to every chunk; the attention-sink result of Rolling Forcing / ID-Forcing), the frame-0 guide plus the relay give the join its place and pose. Pass = b* back near clip 1, `overlap.x_median` <= 2.5, no background jump in frames 0-10. Second variant with `--relay-strength 1.0`.
2. **AdaIN toward clip 1's latent (B).** Add an option `adain_ref: look|clip1` to `add_adain`: `LoadLatent` of clip 1's relay file (already in ComfyUI's input folder) -> `LTXVSelectLatents 0..-1` -> `LTXVAdainLatent(factor 0.3, per_frame False)`; keep the chained look. Then `run retake --clip 3 --adain 0.3`. Hypothesis: a video-latent reference from the same sampler is what the node was tuned for (Lightricks' default path); our image-latent reference may have matched the wrong statistics. Compare factors 0.3 / 0.5 on the same seed; watch saturation (AdaIN 1.0 over-saturated before).
3. **Whole-frame pixel colour match of the chained look (C).** Before `video.unsharp_png`, match `look_chain_k.png` to clip 1's frame 0 (or to the run's look) with Reinhard-in-Lab or MKL (`color-matcher`), full frame, strength 0.7-1.0; optional second pass: costume pixels (Blender mask) matched to the look's costume. `run retake --clip 3 --look-image <matched.png>`. Hypothesis: the frame -1 image is the proven lever (the fresh Qwen look fixed the suit), and a colour-matched copy of the same frame keeps the pose, so the character does not step and the join does not jump. If it works, make it `chain_colour "match"` and run it for every later clip; if the relay still drags the colour, combine with experiment 2.

If all three fail on the same seed, the next structural step is E (anchors for the whole shot made up front, start and end of each clip, pose-matched) — FramePack's endpoints-first at the shot scale — and F as the cosmetic fallback for deliveries.
